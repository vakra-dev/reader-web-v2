Reader and Browserbase both provide cloud browser sessions, but they approach the problem from opposite directions. Browserbase is a managed cloud browser platform with an AI automation SDK. Reader is a cloud web infrastructure platform with an open source core that includes browser sessions alongside scraping and crawling. This comparison covers what each tool does, how they handle browser automation, their AI integration approaches, and their open source licensing.

## What Browserbase Does

Browserbase is a cloud browser platform designed for AI agents and browser automation. You connect to a managed headless browser over CDP, run your automation, and Browserbase handles the infrastructure: browser provisioning, CAPTCHA solving, session recording, and stealth.

The platform includes several products that work together.

**Stagehand** is Browserbase's open source AI browser automation SDK, licensed under MIT with 22,000+ GitHub stars. It provides four primitives for controlling browsers with natural language. `act` performs browser actions from plain English instructions (click, fill, navigate, scroll). `extract` pulls structured data from any page with Zod schema validation. `observe` surfaces what is actionable on a page before you commit to an action. `agent` runs multi step workflows autonomously when you need end to end execution.

Stagehand v3 is multi language: TypeScript, Python, Go, Ruby, Java, Rust, and a REST API for direct use from Claude Code, MCP servers, curl, and n8n. It is browser driver agnostic, working with Playwright, Puppeteer, or any CDP compatible driver without requiring a specific one internally.

**Director** is a no code tool that converts English instructions into Stagehand workflows without writing any code.

**Model Gateway** lets you route LLM calls through your Browserbase API key, supporting OpenAI, Anthropic, and Gemini with no separate accounts or credentials needed. Switching models is a one line change.

Browserbase also provides session replay for debugging (watch exactly what the browser did), automatic action caching that skips LLM inference on repeat actions, prompt observability, and an MCP server.

## What Reader Does

Reader is a cloud web infrastructure platform for AI, available at reader.dev. The managed platform handles scraping, crawling, and browser automation through a single API. The core engine is open source under the Apache 2.0 license, so teams can also self host the entire platform on their own infrastructure.

Reader provides three primitives. Scrape takes any URL and returns clean, LLM ready markdown through Supermarkdown, a Rust HTML to markdown engine. Crawl discovers and extracts content across entire domains using BFS link discovery with configurable depth and page limits. Browser creates cloud browser sessions with full CDP compatibility.

When you create a browser session through Reader's cloud platform, you get back a CDP WebSocket endpoint. Your existing Playwright or Puppeteer scripts connect directly without modification. The browser sessions include stealth features built on Ulixee Hero: TLS fingerprinting, DNS over TLS, WebRTC IP masking, canvas and WebGL randomization, and navigator.webdriver spoofing. Tiered proxy pools (datacenter and residential) with automatic escalation handle IP reputation.

Reader also includes an MCP server (`@vakra-dev/reader-mcp`) with nine tools: scrape, batch scrape, crawl, discover, extract, browser session creation, job status, job cancellation, and credit checking. The managed platform offers 1,000 free pages per month with no credit card required.

## Browser Sessions: Two Architectures

Both platforms give you cloud browser sessions over CDP. The difference is what sits on top.

### Browserbase: AI SDK on top of managed browsers

Browserbase's architecture puts Stagehand between you and the browser. Instead of writing `page.click('.submit-button')`, you write `stagehand.act('click the submit button')`. The AI interprets your intent, finds the right element, and performs the action. If the site changes its DOM structure, Stagehand's self healing adapts without breaking your script.

This is powerful for workflows where page structure is unpredictable. A checkout flow that changes layout between A/B tests. A form that renders differently based on user state. A page that rearranges elements between deployments. Stagehand handles these variations because it works from intent rather than selectors.

The tradeoff is that every AI powered action requires LLM inference. This adds latency and cost per step. Browserbase mitigates this with automatic action caching: once a workflow runs successfully, repeat executions skip the LLM and replay the cached actions. When the site changes, Stagehand detects the break and re engages the AI.

### Reader: Raw CDP on top of stealth browsers

Reader's architecture gives you the raw CDP connection to a cloud hosted browser. You write standard Playwright or Puppeteer code against Reader's managed browser that has stealth features baked in. There is no AI layer between you and the browser.

This is powerful for workflows where you know exactly what to do. Logging into a known portal, navigating a specific dashboard, filling a form with defined fields. Your existing Playwright scripts connect to Reader's CDP endpoint and work without modification. The stealth layer (TLS fingerprinting, WebRTC masking, proxy rotation) handles anti bot detection transparently.

The tradeoff is that you are responsible for writing the automation logic. If a site changes its selectors, your script breaks until you update it. There is no AI self healing. But there is also no LLM inference cost per action, no latency from AI processing, and no dependency on model availability.

## AI Agent Integration

Browserbase and Reader take fundamentally different approaches to AI agent integration.

**Browserbase builds the agent layer.** Stagehand is an AI agent SDK. The four primitives (act, extract, observe, agent) are designed to be the interface between your agent framework and the browser. Model Gateway handles LLM routing. Director offers no code English to automation. The philosophy is: Browserbase provides the AI powered browser, you provide the goal.

**Reader provides the tools, you build the agent.** Reader's MCP server exposes nine tools (scrape, crawl, browser sessions, extract, discover) that any agent framework can call. The scrape and crawl tools return clean markdown that goes directly into agent context windows. The browser tool returns a CDP endpoint that agents can automate with existing Playwright or Puppeteer logic. The philosophy is: Reader provides web access primitives, you bring your own agent logic.

For teams using Claude Code, Cursor, or other MCP compatible tools, both approaches integrate cleanly. Browserbase has an MCP server. Reader has an MCP server. The difference is whether the AI reasoning happens inside the browser tool (Browserbase) or outside it (Reader).

## Scraping and Crawling

This is the clearest product gap between the two.

**Reader** includes scraping and crawling as core primitives alongside browser sessions. Scrape any URL to clean markdown. Crawl entire domains with BFS discovery, depth limits, page limits, and URL pattern filtering. The output is clean markdown processed through Supermarkdown (Rust, single pass O(n) conversion). These primitives work independently of browser sessions for pages that do not need full browser rendering.

**Browserbase** is a browser platform. It does not have a scrape or crawl endpoint. To get content from a page, you create a browser session and use Stagehand's extract primitive or Playwright's content extraction. There is no built in BFS link discovery, no multi page crawling, and no HTML to markdown conversion pipeline.

If your use case is "give me clean markdown from 500 pages across a documentation site," Reader handles this with a single crawl call. With Browserbase, you would need to build the crawling logic yourself on top of their browser sessions.

If your use case is "navigate a complex multi step workflow with AI driven decisions," Browserbase's Stagehand handles this natively. With Reader, you would write the workflow logic yourself against the CDP connection.

## Open Source and Self Hosting

**Browserbase's Stagehand** is fully open source under the MIT license. The SDK source code is on GitHub across language specific repositories. Stagehand works locally with any Chromium browser without Browserbase. When you need production infrastructure (CAPTCHA solving, session replay, action caching, managed browsers), you connect Stagehand to Browserbase's cloud. The cloud infrastructure itself is not open source or self hostable.

**Reader** operates as a managed cloud platform at reader.dev and is simultaneously fully open source under the Apache 2.0 license. The entire engine, including scraping, crawling, browser pool management, stealth stack, and Supermarkdown conversion, is on GitHub. Teams can use the managed cloud platform for zero ops, or clone the repository and deploy the complete platform on their own servers. There are no features gated behind the managed platform. Everything available in the cloud is available in the open source version.

Both platforms have open source SDKs (Stagehand MIT, Reader Apache 2.0). The difference is in the infrastructure layer: Browserbase's cloud is closed, Reader's cloud engine is open.

## When to Pick Each Tool

### Choose Browserbase if:

You are building AI browser agents where natural language control is the primary interface. You want self healing automation that adapts when sites change their DOM. You need session replay and debugging tools for browser automation. You want Model Gateway to simplify LLM provider management. You prefer a managed service with no browser infrastructure to maintain.

### Choose Reader if:

You need scraping, crawling, and browser sessions in a single cloud platform. You want raw CDP access with stealth features rather than an AI layer on top. You need clean markdown output from web pages for LLM pipelines. You want Apache 2.0 open source licensing with the option to self host the same platform you use in the cloud. You want to use your existing Playwright or Puppeteer scripts against cloud browsers without any framework changes.

## Getting Started with Reader

Reader offers 1,000 free pages per month at [reader.dev](https://reader.dev) with no credit card required.

```python
from reader_py import ReaderClient

client = ReaderClient(api_key="rdr_your_key")

# Scrape a page to clean markdown
result = client.read(url="https://example.com")
print(result.data.markdown)

# Create a browser session
session = client.sessions.create(max_duration_ms=300000)
print(session.ws_endpoint)  # Connect with Playwright or Puppeteer
```

```javascript
import { ReaderClient } from "@vakra-dev/reader-js";

const reader = new ReaderClient({ apiKey: "rdr_your_key" });

// Scrape a page to clean markdown
const result = await reader.read({ url: "https://example.com" });
console.log(result.data.markdown);

// Create a browser session
const session = await reader.sessions.create({ maxDurationMs: 300000 });
console.log(session.wsEndpoint); // Connect with Playwright or Puppeteer
```

You can also use the API directly with curl:

```bash
curl -X POST https://api.reader.dev/v1/read \
  -H "x-api-key: rdr_your_key" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com"}'
```

Full documentation is at [docs.reader.dev](https://docs.reader.dev). Source code is on [GitHub](https://github.com/vakra-dev/reader).

## Conclusion

Browserbase and Reader are both cloud platforms that solve different problems with browsers. Browserbase provides an AI powered browser platform where Stagehand handles the reasoning and you provide the goal. Reader provides a cloud web infrastructure platform where you get raw CDP access, scraping, and crawling through a single API, with the option to self host the same engine.

If you need AI driven browser automation with self healing and no code options, Browserbase is purpose built for that. If you need scraping, crawling, and browser sessions under one roof with Apache 2.0 licensing and the flexibility of managed or self hosted deployment, Reader is built for those requirements.
