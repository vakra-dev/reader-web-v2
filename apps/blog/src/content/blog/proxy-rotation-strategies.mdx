Proxy rotation is the practice of routing your scraping requests through different IP addresses to avoid detection and blocking. Without rotation, a single IP sending hundreds of requests to the same site gets flagged and blocked within minutes. With rotation, each request appears to come from a different user, spreading the load across many IPs and reducing the risk of any single IP being banned.

But proxy rotation is not just "use a different IP for each request." The type of proxy, the rotation strategy, the health of the proxy pool, and the concurrency per proxy all affect your success rate. This guide covers each of these dimensions and how they interact.

## Types of Proxies

Not all proxies are equal. The type of IP address determines how the target site perceives your request.

### Datacenter Proxies

Datacenter proxies use IP addresses from cloud hosting providers (AWS, GCP, Azure, OVH, Hetzner) and commercial datacenter operators. They are fast (low latency, high bandwidth) and cheap (the lowest cost per request of any proxy type).

The problem is that [anti bot systems](/blog/anti-bot-detection) maintain blocklists of known datacenter IP ranges. A significant percentage of bot traffic originates from cloud providers, so traffic from these ranges receives elevated scrutiny by default. Many protected sites block datacenter IPs outright for sensitive pages (login, checkout, search results).

**Use datacenter proxies for:** Sites with light or no anti bot protection. Internal tools and staging environments. High volume scraping where the targets are not protected. Initial requests before switching to residential.

### Residential Proxies

Residential proxies use IP addresses assigned to real homes by Internet Service Providers (ISPs). They have significantly higher trust scores because most web traffic from residential IPs is legitimate. Anti bot systems treat residential traffic with far less suspicion than datacenter traffic.

Residential proxies are sourced through SDKs embedded in consumer applications. Users of these applications opt in to share their internet connection in exchange for free access to the app. The proxy provider routes scraping traffic through these connections. Reputable providers (Bright Data, Oxylabs, IPRoyal) publish their ethical sourcing practices and verify user consent.

Residential proxies are more expensive than datacenter (typically 3 to 10 times the cost per request) and slower (real home internet connections have higher latency and lower bandwidth than datacenter connections).

**Use residential proxies for:** Sites with [Cloudflare](/blog/bypass-cloudflare), DataDome, Akamai, or other anti bot systems. E-commerce sites, social media platforms, and any target that blocks datacenter IPs. Scraping at moderate volume where success rate matters more than cost.

### Mobile Proxies

Mobile proxies use IP addresses from mobile carriers (Verizon, AT&T, T-Mobile, Vodafone). These have the highest trust scores because mobile carrier IP ranges use carrier grade NAT, meaning many legitimate users share the same IP. Anti bot systems are reluctant to block mobile IPs because blocking one IP could affect thousands of real users.

Mobile proxies are the most expensive proxy type and the slowest (mobile network latency). They are typically used as a last resort for the most aggressively protected targets.

**Use mobile proxies for:** Sites that block even residential IPs. The most protected targets (LinkedIn, airline booking sites, heavily defended e-commerce). When no other proxy type succeeds.

### ISP Proxies (Static Residential)

ISP proxies are IP addresses purchased directly from Internet Service Providers. They combine the trust level of residential IPs (they are real ISP assigned addresses) with the stability of static IPs (they do not rotate automatically and do not change between requests).

ISP proxies are ideal for sessions that need to maintain the same IP across multiple requests (login flows, multi page checkout, authenticated scraping) while still appearing as residential traffic.

**Use ISP proxies for:** Authenticated workflows requiring a stable IP. Long running sessions where IP changes would trigger re authentication. Moderate volume scraping that needs residential trust without rotation overhead.

## Rotation Strategies

How you rotate proxies matters as much as which proxies you use.

### Per Request Rotation

Every request gets a different IP. This is the simplest strategy and the default for most proxy providers. It maximizes the distribution of requests across IPs, minimizing the chance of any single IP being flagged.

```python
import random

proxies = [
    "http://user:pass@proxy1:port",
    "http://user:pass@proxy2:port",
    "http://user:pass@proxy3:port",
    # ... more proxies
]

def get_random_proxy():
    return {"http": random.choice(proxies), "https": random.choice(proxies)}

# Each request uses a different proxy
for url in urls:
    response = requests.get(url, proxies=get_random_proxy())
```

**Advantages.** Maximum IP diversity. Simple implementation. Works well for stateless scraping (each page is independent).

**Disadvantages.** Breaks session based workflows. If the target site sets cookies on request 1 and expects them on request 2, different IPs for each request may invalidate the session. Some sites bind sessions to IPs and block requests when the IP changes mid session.

### Sticky Sessions

A sticky session maintains the same IP for a series of related requests, then rotates to a new IP for the next series. Most proxy providers support this through a session ID parameter: all requests with the same session ID route through the same proxy.

```python
# Same proxy for all requests in a session
session_proxy = random.choice(proxies)
session_config = {"http": session_proxy, "https": session_proxy}

# All pages in this scraping session use the same IP
for page in range(1, 11):
    url = f"https://example.com/products?page={page}"
    response = requests.get(url, proxies=session_config)
    time.sleep(1)

# New session, new proxy
session_proxy = random.choice(proxies)
session_config = {"http": session_proxy, "https": session_proxy}
```

**Advantages.** Maintains cookie and session state. Required for login flows, multi page checkout, and authenticated scraping. Appears more natural (real users browse from the same IP).

**Disadvantages.** Concentrates requests on fewer IPs. The sticky IP gets more requests and is more likely to be flagged. Session duration must be balanced: too short loses state, too long burns the IP.

**Typical sticky session duration:** 1 to 10 minutes for light scraping. 10 to 30 minutes for authenticated workflows. Some providers offer sessions up to 60 minutes.

### Geo Targeted Rotation

Route requests through proxies in specific geographic locations. This matters for two reasons.

First, some sites serve different content based on the visitor's location. An e-commerce site shows different prices, products, and promotions to users in different countries. A news site shows different stories to US vs UK visitors. To get location specific data, your proxy must be in the target location.

Second, geographic consistency is a trust signal. If your User Agent claims to be in the US (Accept-Language: en-US) but your IP is in Brazil, the mismatch raises suspicion with anti bot systems.

```python
# Request through a US residential proxy
us_proxy = "http://user:pass@us-residential:port"
response = requests.get(url, proxies={"http": us_proxy, "https": us_proxy})

# Request through a UK residential proxy for UK-specific data
uk_proxy = "http://user:pass@uk-residential:port"
response = requests.get(url, proxies={"http": uk_proxy, "https": uk_proxy})
```

**Use geo targeting for:** Price comparison across regions. Location specific content scraping. Maintaining geographic consistency between IP location and Accept-Language header.

### Tiered Rotation

Start with the cheapest proxy type and switch to more expensive types when cheaper ones fail. This optimizes cost while maintaining success rate.

```python
def scrape_with_tiered_rotation(url, headers):
    # Tier 1: Datacenter (cheapest)
    response = requests.get(url, headers=headers,
                           proxies=get_datacenter_proxy())
    if response.status_code == 200:
        return response

    # Tier 2: Residential (more expensive, higher trust)
    response = requests.get(url, headers=headers,
                           proxies=get_residential_proxy())
    if response.status_code == 200:
        return response

    # Tier 3: Mobile (most expensive, highest trust)
    response = requests.get(url, headers=headers,
                           proxies=get_mobile_proxy())
    if response.status_code == 200:
        return response

    return None  # All tiers failed
```

This strategy uses datacenter proxies for the majority of requests (where they succeed) and only spends on residential or mobile proxies for requests that fail at lower tiers. For most workloads, datacenter handles 60 to 80 percent of requests, residential handles 15 to 30 percent, and mobile is rarely needed.

## Health Checking and Pool Management

A proxy pool is only as good as its maintenance. Dead proxies, slow proxies, and banned proxies waste time and credits. Active pool management keeps your rotation effective.

### Track Success Rate per Proxy

Monitor the success rate (HTTP 200 responses with actual content) for each proxy in your pool. A proxy that returns 403s, CAPTCHAs, or empty responses is burned.

```python
from collections import defaultdict

proxy_stats = defaultdict(lambda: {"success": 0, "fail": 0})

def record_result(proxy, success):
    if success:
        proxy_stats[proxy]["success"] += 1
    else:
        proxy_stats[proxy]["fail"] += 1

def get_success_rate(proxy):
    stats = proxy_stats[proxy]
    total = stats["success"] + stats["fail"]
    return stats["success"] / total if total > 0 else 1.0

def get_healthy_proxy(proxies, min_rate=0.7):
    healthy = [p for p in proxies if get_success_rate(p) >= min_rate]
    if not healthy:
        # All proxies below threshold, use the best one
        return max(proxies, key=get_success_rate)
    return random.choice(healthy)
```

### Bench Failed Proxies

When a proxy fails (returns a 403, CAPTCHA, or timeout), do not immediately reuse it. Bench it for a cooling period. The IP may be temporarily flagged by the target site, and reusing it immediately wastes requests and could extend the ban.

```python
import time

benched_proxies = {}  # proxy -> bench_until_timestamp

def bench_proxy(proxy, duration_seconds=300):
    benched_proxies[proxy] = time.time() + duration_seconds

def is_benched(proxy):
    if proxy in benched_proxies:
        if time.time() < benched_proxies[proxy]:
            return True
        del benched_proxies[proxy]
    return False

def get_available_proxy(proxies):
    available = [p for p in proxies if not is_benched(p)]
    if not available:
        # All benched, wait for the soonest to unblock
        soonest = min(benched_proxies.values())
        time.sleep(max(0, soonest - time.time()))
        return get_available_proxy(proxies)
    return get_healthy_proxy(available)
```

A 5 minute bench period works for most sites. Sites with longer ban durations (some e-commerce platforms ban IPs for hours) may need longer cooling periods.

### Auto Recycling

Even healthy proxies should be retired after a certain number of requests or time period to prevent gradual reputation degradation. A proxy that has been used for 100 requests without issues is still accumulating request history on the target site. Retiring it before it gets flagged is proactive prevention.

```python
proxy_usage = defaultdict(lambda: {"requests": 0, "started": time.time()})

MAX_REQUESTS = 100
MAX_DURATION = 1800  # 30 minutes

def should_recycle(proxy):
    usage = proxy_usage[proxy]
    if usage["requests"] >= MAX_REQUESTS:
        return True
    if time.time() - usage["started"] >= MAX_DURATION:
        return True
    return False

def use_proxy(proxy):
    proxy_usage[proxy]["requests"] += 1
```

### Concurrency Limits per Proxy

Sending too many concurrent requests through a single proxy increases the chance of that IP being flagged. Anti bot systems track request frequency per IP. Ten concurrent requests from one IP in one second is a bot signal.

Limit concurrency to 1 to 3 concurrent requests per proxy. This distributes load across the pool and prevents any single IP from appearing to generate unusually high traffic.
